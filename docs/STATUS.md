## Measured values (Step 2 manual session, user-reported from HUD screenshots)
Single session, normal light, MacBook Air M4 (Mac16,12), built-in camera, 640x480 preset, debug build, Vision revision 3. Not a benchmark: one sitting, a handful of readings, dim room not tested.
- Frame rate: **30.0 fps**.
- Capture→pose latency in THIS (older) Step 2 session: **about 94–97 ms total = delivery ~81–82 ms + Vision ~13–15 ms** (our filter/state machine cost is inside the total and not separated). **The ~81 ms (in this session) is delivery time** (from the frame's sample timestamp to our capture callback starting), not Vision. This is the dominant term; its cause is unknown (investigation is in the Step 5 plan). Note this excludes any delay before the sample timestamp, so true photon-to-pose latency is at least this much. **In the three later self-test runs (07:45, 08:12, 14:58) it read about 63 ms delivery (61-63) + 18 ms Vision = 81 ms total (79-81)** (see "Step 2d findings"); the two sets differ and the reason is unknown. Neither figure includes the One-Euro filter's own lag (see "Step 2g findings").
- `AVCaptureConnection`: `isVideoMirrored = false`, `videoRotationAngle = 0°` (so the mirroring compensation was not exercised on this Mac).
- Vision confidence: 0.87–0.89 with one face (so it is not a constant 1.0 here; still a weak signal).
- With all invert boxes unticked: raw yaw +25.3° → mapped +25.3°; raw pitch −11.7° → mapped +11.7°; raw roll −3.5° → mapped −3.5°. This only shows the mapping arithmetic (pitch negated); it does not say which physical direction the head was turned.

## Known limitations of Step 2 (stated, not measured)

## ThreadSanitizer finding (2026-11-04, worth remembering)

## PoseMailbox stress-test finding (2026-11-04): a clock-dependent TEST, not a mailbox bug
**Symptom.** During the first 18-mutation run, `concurrentStressHasNoTornReadsAndMonotonicSequences` failed together with a loss-analyzer test, although the injected bug (M13) touched unrelated code.

**Classification: timing-dependent test (a wall-clock hang guard). Not a mailbox bug, and not ordinary load flakiness.**

Evidence:
1. **Timeline** (`pmset -g log` plus source-file mtimes). The run started 17:50:36 with the lid closed on battery at 3%. The Mac slept at 17:50:57 and 18:01:15, so the script advanced only during brief maintenance wakes (36 minutes in total; the same run takes about 70 s on a settled machine). M13's run ended at 18:25:58, the same second as the wake that ended a 97 s sleep (18:24:21 → 18:25:58): its test process was frozen mid-run.
2. **Mechanism in the code.** The reader ended on `Date() < deadline`, a 60 s *wall-clock* deadline, and wall-clock time keeps running during sleep. The other assertions (`torn`, `backwards`, `newReads`) cannot depend on time, and the algorithm cannot produce torn or backwards reads (the reader only swaps in a slot published after its current one; the `acq_rel` exchanges give the happens-before).
3. **Reproduction.** Freezing the test process (SIGSTOP) for 65 s during a 100M-iteration run made exactly one assertion fail, `r.lastSeq == total` (the reader had seen 22.4M of 100M values), while torn/backwards stayed green: the signature of the original failure.
4. **No failures without a freeze.** 170 valid runs on the unmodified code, 0 failures: stress test alone ×60, whole suite ×30, under ThreadSanitizer ×40 (30 stress + 10 whole suite), with 20 busy processes on 10 cores ×40 (30 stress + 10 whole suite). (An earlier loaded set was INVALID and is not counted: the bundles were still TSan-instrumented from the previous phase and aborted with "Interceptors are not working". Redone correctly.)
5. **Re-run.** The same 18 mutations on a settled machine caught M13 only with its own test (no stress-test failure).

**Fix (test only).** The reader now stops when the writer has finished and it has done one more read. That read starts after the final publish, so a latest-value mailbox must return the final sequence: the verdict uses no clock. Same 65 s freeze and 100M iterations: old design **fails**, new design **passes** (79.5 s, 196M reads). The new test still catches real mailbox bugs: a no-atomics single slot fails `torn == 0`; a reader that never swaps in new data fails `lastSeq == total` in 28 ms (the old design would have spun toward its deadline). Repeats of the new test: 40 plain, 30 under load, 30 under TSan, 0 failures; a 10M-iteration TSan soak is clean.

**The same class of hazard, found by auditing the rest of the suite and fixed:**
- `SimulatedHeadPoseProvider.stop()` was a **real race in production code** (added in Step 2c): it cancelled the timer without waiting for a tick already running, so one more detection could arrive after `stop()` returned, contradicting the protocol's "blocks until released". It now drains the in-flight tick. Regression test `noDetectionIsDeliveredAfterStopReturns`: **6/6 runs fail without the drain, 0/6 with it**.
- `HeadTracker.stopWatchdog()` had the same hole for watchdog snapshots; fixed the same way. Its first regression test was too weak (0/6 failures without the fix, so it proved nothing); it now uses a deliberately slow snapshot handler to keep a tick in flight: **6/6 fail without the drain, 0/6 with it**.
- Fixed sleeps and exact count windows replaced by `waitUntil` (deadline on `SuspendingClock`, which does not advance during sleep) and by an upper bound derived from the measured elapsed awake time; a test that started a real watchdog and asserted an exact snapshot count now disables the watchdog.
Rule recorded in CLAUDE.md: tests never derive a verdict from a wall-clock deadline or fixed sleep.

## App Nap finding (2026-11-04): the app must hold an activity assertion while tracking
While checking the default report path with a simulated run, the loss test began to fail (INCOMPLETE or FAIL, state flapping). The report's own statistics showed why: every run delivered 26.4 fps on average with 125–131 ms frame gaps (≈790 of 900 frames) instead of 30.0 fps and ≈35 ms. Elimination: a bare 30 Hz `DispatchSourceTimer` in a command-line process in the same minute was perfectly regular (33.3 ms, max < 39 ms, at several QoS and leeway settings); the app used only 0–7% of one core and its thread stacks were parked, so nothing was busy or blocked; launching through LaunchServices did not help (foreground launch: 26.4 fps too). Confirmed with the documented `NSAppSleepDisabled=YES` switch on the dev bundle (since removed): **900 frames, 30.0 fps, 33/34/34 ms, PASS**, versus the same minute without it: **789 frames, 26.3 fps, 38/100/130 ms, INCOMPLETE**. So macOS was App-Napping the app because its window was hidden behind others, coalescing its timers.

**Fix.** `HeadTrackingModel` holds `ProcessInfo.beginActivity([.userInitiatedAllowingIdleSystemSleep, .latencyCritical])` from a successful start until stop (API checked in NSProcessInfo.h and by compiling; the "allowing idle system sleep" variant does not keep the Mac awake). With it, simulated runs under the same conditions: 3/3 PASS, 900 / 897 / 900 frames, 30.0 fps. The report now says so when frames stall (statistics note for gaps over 100 ms, loss-test note for gaps over 150 ms); run 2 of those 3 showed a single 134 ms stall and the note fired while the verdict stayed PASS. **Not verified:** whether real camera frame delivery (an AVFoundation callback, not a timer) is affected by App Nap; the assertion is held there too.

## Step 2g findings (2026-11-05): filter characterization, SYNTHETIC
**Every number in this section is SYNTHETIC: the real `HeadPosePipeline` (default One-Euro parameters minCutoff 1.0 Hz, beta 0.5, derivative cutoff 1.0 Hz; default quality gate) driven by exact, noise-free or seeded-noise orientations at a perfectly regular 30 fps. The harness is `Tests/SpatialAudioCoreTests/FilterCharacterizationTests.swift`; `SA_PRINT_FILTER_TABLE=1 swift test --filter FilterCharacterization` prints the tables below.

**Method.** *Constant turn:* the head sits still for 1 s (the gate locks), then turns about yaw at constant speed for 4 s; the lag is the mean over the LAST second of how far the output is behind the input at the same frame (signed, positive = behind); "lag spread" is max minus min over that second (0 = converged); time lag = lag / speed. *Settle:* the head then stops; the time until the output stays within the tolerance of the final orientation for the rest of a 3 s window (resolution one frame, 33 ms). *Jitter:* a still head with independent seeded Gaussian noise (Box-Muller, same seed for every sigma) on yaw, pitch and roll, 3,000 frames, the first 90 discarded; gain = standard deviation of the output's Euler angle / that of the generated input, per axis.

**What the numbers show (synthetic).**
- The filter's lag is large and speed-dependent in the way its design says: the angular lag grows with speed (5.1° at 45 deg/s to 13.8° at 360 deg/s) while the time lag shrinks (114 ms to 38 ms) because the cutoff rises with speed. The measured lag equals the lag predicted from the cutoff law (a first-order smoother with cutoff = minCutoff + beta x speed has a steady lag of step x (1 - a) / a per frame) to within 0.5% at every speed, so the harness and the pipeline agree with the filter's own formula. For this beta the continuous-time limit of the angular lag at very high speed is 1 / (2 pi beta) = 0.318 rad = 18.2°.
- After a stop the output is within 1° after 200-300 ms and within 0.1° after 500-667 ms (to the 33 ms frame resolution).
- Jitter is cut to about 0.35 (sigma 0.5°) to 0.52 (sigma 4°) of the input spread, rising with the noise because the noise itself raises the speed estimate and so the cutoff. At sigma 4° the output still wanders with a standard deviation of about 2°. So at rest the filter trades roughly 0.35-0.5 of the jitter for the lag above while moving; whether that trade is right is not decided here.
- For scale only (not a sensor-noise measurement, and those windows include real head motion): the robust spreads of the real "stay still" windows in the 14:58 report were 0.3-1.8° (3.65° in the first baseline).
- **The measured 81 ms (sample timestamp to pose ready, three real runs) does not include this algorithmic lag**; in head-motion terms the two add up (this synthetic filter lag is 89 ms at 90 deg/s, 38-114 ms across the speeds), and the audio side (the pose pump's 20 ms smoothing, the audio buffers) adds more that has not been measured. No end-to-end figure is claimed.
- **No test anywhere pins the default One-Euro parameters:** changing the default beta to 0 or minCutoff to 2 Hz breaks no test in the whole Core suite (mutation check below). That is by design for these new tests (they assert properties, not targets), but it means a later tuning change is not guarded by any test, only recorded by this table.

Validity is in `mFlags`: `kAudioTimeStampSampleTimeValid` = bit 0, `kAudioTimeStampHostTimeValid` = bit 1, `kAudioTimeStampRateScalarValid` = bit 2 (CoreAudioBaseTypes.h). The headers do not say which of them a tap's aggregate device sets.

**The callback change (and only this).** `SATapProbeRecord` grew from 32 to 48 bytes: `inputHostTime` (u64) and `inputSampleTime` (double), plus three bits in the existing `flags`: no `inInputTime` pointer (32), host time not valid (64), sample time not valid (128). Validity comes from `mFlags` only, never from the value (a sample time of 0 is legitimate); an invalid field is stored as 0 so garbage never reaches the report; a NULL `inInputTime` sets all three bits. The release object is 101 instructions (82 before), 0 calls, no branch out. **Not recorded, named as candidates:** the input `mRateScalar` ("the ratio of actual host ticks per sample frame to the nominal host ticks per sample frame", marked valid by its own bit) and the validity of `inNow` itself (the callback has always read `inNow->mHostTime` without looking at `inNow->mFlags`; this step did not change that, by instruction). The record buffer for a 600 s run is about 600,000 x 48 bytes = 29 MB (from the sizes in the code, not measured).

**The report (schema 3).** The window table has `inNow` and `input` columns for the SAME callbacks (windows are bucketed by `inNow` for both, so a difference is the stamp's, not the membership's): implied frames/s, ppm against the declared rate, cumulative frame offset, plus the number of usable input callbacks per window. For each estimator over the whole run: a least-squares fit of the offset (frames delivered minus declared rate x stamp time, from the estimator's own first callback) against stamp time: the slope as ppm of the declared rate with one standard error, the SD and peak-to-peak of the offset about the line in frames, and **the resolution floor**: `peak-to-peak / (declared rate x time) x 1e6` ppm, for the whole run and for one 10 s window. Also: how many callbacks had a valid input host time / sample time / no pointer, `inNow` minus input host time (ms, min / median / max), and sample-time continuity (did the HAL's counter advance by exactly the frames delivered). Sentences in words are generated from these numbers and say "NOT larger than the jitter" when the fitted offset change over the run is not larger than the scatter.

**What each estimator can and cannot resolve (printed in every report).** Both compare the tap's frames with a HOST-clock timestamp per callback: the tap against the host clock, nothing about the output device's clock. `inNow` carries the scheduling variation; the input host time may be steadier but what it refers to for a tap-only aggregate is not documented, and whether the HAL smooths it with its own clock model is UNVERIFIED, so a very straight input line is NOT proof of a steady clock. **Resolution is arithmetic on the formula, not a measurement of this Mac:** at 48,000 Hz over 600 s one frame of peak-to-peak scatter is 0.0347 ppm (so 1 ms = 48 frames = 1.67 ppm), and within one 10 s window one frame is 2.08 ppm (so 1 ms = 100 ppm). What the scatter really is on this Mac is unmeasured: the run will say. A drift smaller than the printed floor cannot be told from jitter; a short run has a large floor; the standard error assumes independent jitter (UNVERIFIED), the floor does not. Not resolved by either: the output device's drift, tap-versus-output drift, a change of the HAL's own rate during the run (folded into the slope), non-linear drift (the window table shows it). The older whole-run "tap implied" rate on the Rates line uses only the first and last callback, so it is labelled an ENDPOINT estimate in the report (the simulated 25 s run printed -99.7 ppm there and +2.80 ppm from the fit, which is exactly the kind of disagreement the label is for).

**Simulated example (FABRICATED, decides nothing).** The simulated source stamps `inInputTime` on the ideal timeline minus a fixed latency, so its input estimator shows 0.0 frames of scatter and its `inNow` estimator shows the pacing thread's sleep jitter (220 frames peak-to-peak over 25 s, floor 183 ppm in that run). **Design revision (docs/ARCHITECTURE.md, "Reading the ring from two blocks"; PLANNED / UNVERIFIED, no code).** One producer index; one read cursor per block, written only by its block; each block advances only its own cursor by exactly the frames it was asked for, every call, whether or not data was available, so correctness does not depend on the order (or the concurrency) in which the engine runs the two blocks. ### Known limitations of Step 6a3 (stated, not measured)
- Everything about real stamps is UNVERIFIED: whether `inInputTime` is valid for a tap aggregate, whether it is steadier than `inNow` or the HAL's smoothed model, and the real scatter.

### Findings made on the way
- **The scan found a real hidden call in the first release object.** Apple clang turned the zero-fill loop in `SARingRender` into a call to `bzero` (not `memset`). `no_builtin("memset")` did NOT stop it; the bare `__attribute__((no_builtin))` does (tried three spellings against SwiftPM's flags; the unchanged probe reproduced SwiftPM's object, so the probe was faithful). The scan, not the attribute, is the safety net: removing the attribute is now case `z`.
- **SwiftPM compiles C targets with `-Os`, not `-O2`.** The 6a script's `--source` mode uses `-O2`; the variants here use SwiftPM's flags. The design doc's "17 instructions" for the block was a scratch `-O2` spike; the shipped block is 15 instructions with one call.
- **The first versions of three harness checks were wrong, not the library** (each worked out by hand before changing anything): the prime depth was set equal to the serve window and a commit was added before the first read (a correct overrun); a test ring was smaller than its window needed; and my expectation that BOTH readers count a phase mismatch in the first cycle was wrong (the first block of a cycle sees the other's old phase). A Swift helper trapped because `UnsafeMutableAudioBufferListPointer`'s subscript is bounds-checked against `mNumberBuffers`.
- **A TSan false positive in my first stress harness, found on the REAL code:** a write-after-read (the producer overwriting a slot the reader had read a lap earlier). The harness paced the threads with relaxed counters and standalone fences, which is valid C11 but invisible to TSan (it does not model standalone fences). Fixed in the harness by making reader-to-producer progress a real release/acquire edge, and keeping producer-to-reader progress deliberately fence-only so the library's own `w` stays the only edge TSan can see. The library was not changed.
- **ThreadSanitizer is blind to the ordering of relaxed atomics** (the production sample type): it passes a broken `w` protocol there (shown on M01 and M02: exit 0, zero warnings). That is why the TSan run uses the same file compiled with plain float samples and a stress in which a reader is never overtaken; there TSan reports the three ordering mutants as real data races (read in `SARingRender` against the producer's previous write) while the value checks of the same run say `0 failures` (the data happened to be right on this chip). Both facts are in `scripts/tsan-systemaudioring.sh`'s header.
- **Test gaps the first mutation run found in MY harness (all closed, then killed):** M14 (the unsigned-difference underrun test) survived because my underrun scenario committed before every render, so a reader was never further ahead than the producer at the moment of a call; M25 (prime without the `commits < T` guard) survived because the other guard (`depth > w`) hides it whenever commit sizes are equal; M07 (modulo `N-1`, consistently on both sides) survived because the only effect is on an UNPUBLISHED in-flight commit of exactly `maxCommit` frames at the edge of the window; M15 (post-copy check removed) survived the threaded stress even though about 1,500 blocks per run are torn, because a torn block only corrupts data when an in-flight commit lands on exactly the copied frames. Closed with scenarios K, F2, L and J, the last two via test hooks (`SA_RING_TEST_HOOKS`, compiled in only by the deterministic harness; the shipped object is unchanged).
- **Offline engine observation (OFFLINE ONLY, one run, printed by the test):** an `AVAudioEngine` in manual offline rendering with one source node pulled the block 12 times for 128 frames each (1,536 frames), every call had a valid sample time, none was silent, and the reader of the other channel (no node) was never called; the output was the ring's data for that channel (up to a mixer gain the test does not assume). **This says nothing about a real-time device, Bluetooth, or the order in which a real-time engine runs two blocks.**

### Known limitations of Step 6b-1 (stated, not measured)
- Everything about a real tap, a real-time engine, Bluetooth and the real order, frame counts and timestamps of two blocks in one cycle is UNVERIFIED. Whether the sample time is valid in the real graph is unknown (it was valid offline).
- **Starvation after an underrun, and recovery is NOT implemented.** At equal producer and reader rate a reader that has gone ahead of the producer stays starved. That is not only a consequence of departure (i): the design's own underrun row (zeros, the cursor still advances by `F`, late frames dropped) implies the same behaviour unless the control thread re-primes. The control-thread re-prime and the render-side jumps (the overrun jump to `w - T`, the divergence jump) are PLANNED, not implemented here or anywhere; there is no recovery of any kind, so after the first underrun a run would stay silent. (CLAUDE.md now forbids any listening build or audible use of the ring until that recovery is implemented and mutation-checked.)
- **M21 and M22 (the two fences) are UNTESTED.** No detector fails when either is removed, so they rest on the C11 argument in docs/ARCHITECTURE.md alone. The margin argument is checked by the hooks and the stress; the fences by nothing.
- **The TSan evidence for M01 to M03 comes from the PLAIN-SAMPLE build (`-DSA_RING_PLAIN_SAMPLES`), not from the shipped (atomic-sample) build.** On the shipped build TSan passes those three broken variants (shown: exit 0, zero warnings). - Capacity 32768 and prime depth 4 are GUESSES; the real constants leave a factor of eight between prime depth and serve window, the test rings do not.
- Sample values are copied unchanged (a NaN or infinity in the tap reaches the output); stereo Float32 interleaved only; no handling of a format or rate change; lifetime and teardown (when the ring may be freed while the engine or the IO proc could still call it) are Step 6b-2's problem.
- The scan reads the release objects of one build configuration with one toolchain's output format, checks calls and not behaviour, and is a narrow exception to CLAUDE.md's rule.

## Step 6b-2b offline experiment (2026-11-08): does the mixer consume what it pulls? OFFLINE, one Mac, UNVERIFIED for the device path
**Scope.** Code `4e013f5` (tests and analyzer), this record and `scripts/mutate_resampling.py` in a separate commit. **An AVAudioEngine in OFFLINE manual-rendering mode only: no device, no real-time engine, no Bluetooth.** Tags: **[measured offline]** = printed by the opt-in table (`SA_RESAMPLING_TABLE=1 swift test --filter ResamplingConsumptionTable`) on this Mac, 2026-11-08, K = 2000 renders per case, 20 warm-up renders excluded; **[derived]** = arithmetic on those; **[hypothesis, UNVERIFIED]**. Rules kept: new files only (no change to `CSystemAudioRing`, `SASourceNode.m`, the scans, the allow-list, `RingProbeEngine` or any existing test); no new C function and no new call in the render block; output gain above the mixer's own default is set only by a guard that refuses any engine not in manual-rendering mode (tested); single-threaded (produce, render, snapshot, repeat), no sleeps, timers, threads or wall-clock verdicts; only the case-1 controls are asserted.

**Method.** A producer writes the ramp Float(j) x 2^-20 (j = source frame) through the real `SARingIOProc` into the real ring (N = 32768; 512-frame commits until the left reader's fill is at least 4096); two real source nodes at 48 kHz (node 1 muted) feed the main mixer of an offline engine at the output rate; each render yields the left reader's pulled frames and calls (deltas of its counters), its cursor and the left output samples. The analyzer fits (sample x 2^20) against the output index (source frames per output frame times the gain G) and builds the gap g_k = cursor_k - last output sample x 2^20 / G (source frames pulled but not yet played). **Plan, tolerances and predictions were written to scratch files before any code or run** (file time 21:02:15; the plan quotes them): control tolerance = 4 x the quantization step the analyzer derives from the data (0.25 source frames at G = 1 while the ramp stays below 2^20 frames); "near" bands for labelling only: +/- 50 ppm of a hypothesis' ratio deviation and +/- 0.05 frames per render of its gap slope. The mutant list M01-M12 was written at 21:02:15 too, M13-M15 at 21:08:23, all before any mutant ran (the first mutant run started 21:10:23).

**Two things the first table run showed (reported, not hidden).** The first run used the plan's "G measured in case 1 and reused". (1) **That assumption is false:** cases 2-4 all gave slope x G = 0.769650666 = ideal x 0.7071068; case 5 gave 3.000046892 for an ideal 3. So the printed "ratio deviations" of run 1 for cases 2-4 (-292,883.45 ppm) were a gain error, not resampling behaviour (run 1's output is kept in the scratch directory and reproduced as table [A] below). (2) **Prediction P-pull was violated** (below). **Post-hoc change, written down before run 2 (plan addendum, 21:08:23):** G is measured per case with a constant source (the producer writes 0.25; output mean / 0.25; assumes a unity-DC-gain converter, which the numbers below show is true only to about 14 ppm), and a control was added that the DC-derived and ramp-derived G of the control agree within 1e-6 (tolerance written before run 2; it holds). No tolerance of the original plan was changed. The table's [B] analysis uses G per case.

### Predictions and which held
- **P-pull** (case 2 pulls exactly 558, case 3 exactly 480, case 4 exactly 1115, case 5 exactly 1536; a deviation would itself be a finding): **held for 3 and 5, VIOLATED for 2 and 4.** The offline engine pulled 557 or 558 (mean 557.2788, the ideal) in case 2 and 1114 or 1115 (mean 1114.5576, the ideal) in case 4. **The offline path differs from the device path**, where every call asked for exactly 558 (558.00 in every interval, Step 6b-2 real runs).
- **H1** (consumes all pulled frames: ratio deviation +1293.9 / +396.7 ppm in cases 2 / 4, gap flat) and **H2** (consumes the ideal ratio and keeps the surplus: deviation 0, gap +0.7211 / +0.4422 frames per render): **neither held in cases 2 and 4** (label H3 in the plan's terms). In cases 3 and 5 the surplus is 0, so H1 and H2 coincide there (no discriminating power; they served as controls of the method: the ratio deviation was +0.00 and +0.01 ppm, the gap flat).
- **The plan's assumption "G measured in case 1 is reused": false** (see above).
- **Post-hoc category, not a prediction that held (call it H4):** the offline mixer pulls the ideal count on average (a mix of floor and ceil), the measured ratio equals the ideal to 0.00 ppm, and the gap has zero slope: **it consumes what it pulls, and what it pulls is the ideal; there is no surplus to keep or consume.**

### Findings
1. **[measured offline] G is not a constant of the mixer.** 1.000000000 at 48 kHz and 1.000015616 at 16 kHz, but **0.707116547 at 44.1 kHz in all of cases 2, 3 and 4**, i.e. 1/sqrt 2 (0.707106781) within +13.8 ppm [derived], a -3 dB scaling. **I do not know why** the 44.1 kHz output is scaled and the 16 kHz one is not [hypothesis: none; not investigated]. The converter's DC gain is not exactly 1 either (+13.8 and +15.6 ppm [derived] relative to 1/sqrt 2 and 1); the analysis divides by the DC gain, and the ramp then gives ratio deviations of 0.00 and 0.01 ppm, so the ramp and the DC see the same gain.
2. **[measured offline] The offline mixer asks for exactly what it needs, on average:** case 2 mean 557.2788 (ideal 557.27891), case 4 mean 1114.5576 (ideal 1114.55782); one call per render. **[derived]** With a mean pull equal to the ideal, the surplus H2 needs (0.7211 / 0.4422 per render) is 0 in this engine, so **this experiment cannot tell whether a mixer consumes all of a constant 558: the offline engine never asks for one.**
3. **[measured offline] The gap has zero slope, but it is not constant:** peak-to-peak 17.9 (case 2) and 37.2 (case 4) source frames, 2.0 (case 3) and 0.6 (case 5), against quantization steps of 0.09 to 0.25. **[derived]** No tolerance was written for cases 2-5 (only the control is asserted); the oscillation is the converter's own buffering and the 557 / 558 alternation [hypothesis, UNVERIFIED: not investigated].
4. **[hypothesis, UNVERIFIED] For the device path:** the Step 6b-2 real runs show a constant 558 per call at 86.13 calls per second and a ring that drained 62 frames per second. This experiment gives NO evidence about whether the device-path mixer consumes all 558 (the drain would then be real) or consumes the ideal ratio and keeps the surplus, because its offline counterpart pulls a different (ideal-average) sequence. Why the two paths pull differently is not known.
5. **Thread, [measured offline] / header:** `AVAudioEngine.h` describes offline mode only as "without any realtime constraints" and does not say which thread calls a source block. Evidence collected, not proof: the counters never changed after `renderOffline` returned (2000 renders x 5 cases), a repeat run was identical, the process gained one thread at the engine start and none during the renders. **Which thread runs the block is UNVERIFIED; nothing contradicted "the calling thread".** If it had been another thread the plan was to stop and report.
