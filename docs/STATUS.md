## Known limitations of Step 2 (stated, not measured)
- `VNObservation.confidence` is a weak signal (Apple says it can be a constant 1.0; measured 0.87–0.89 in one session). Our own quality signal now gates tracking, but its thresholds are untuned guesses.
- The watchdog handles a stalled or silent camera. It does not handle sleep/wake or device unplug explicitly (Step 6 covers sleep/wake for audio); a tick after wake may see a large frame age and simply treat it as loss.
- Sleep/wake and camera-unplug handling are not implemented.
- Only the largest face is used. No camera selection UI.
- The new Swift-native Vision API (`DetectFaceRectanglesRequest`) is macOS 15+, so the legacy `VN*` classes are used to keep the 14.0 minimum.
- The self-test cannot know which way you actually moved; a tilt of the wrong ear silently inverts the roll result.
- All self-test thresholds (movement, noise, steadiness, leakage, jump, stall) are untuned proposals; real data may show them to be too strict or too loose. INCONCLUSIVE is the designed outcome for weak data.
- The self-test stops the camera when it finishes (to verify the release), so verifying applied signs needs another Start camera.
- Reports from a throttled or overloaded run are flagged by a stall note, but nothing prevents you from running while the Mac is busy.

## ThreadSanitizer finding (2026-11-04, worth remembering)
`swift test --sanitize=thread` initially stayed silent on a deliberately injected race in the C target: a plain struct assignment compiles to `___tsan_memcpy`, which this TSan runtime did not race-check, even though the code was instrumented. Fixed by copying the six fields individually in `CPoseMailbox.c`. After that, both `scripts/tsan-mailbox.sh` and `swift test --sanitize=thread` flag a relaxed-ordering mutation (which produced zero torn reads, i.e. only TSan catches it) and a no-atomics mutation, and stay clean on the real code. Lesson: a green TSan run only counts if TSan has been shown to fail on a broken variant.

## PoseMailbox stress-test finding (2026-11-04): a clock-dependent TEST, not a mailbox bug
**Symptom.** During the first 18-mutation run, `concurrentStressHasNoTornReadsAndMonotonicSequences` failed together with a loss-analyzer test, although the injected bug (M13) touched unrelated code.

**Classification: timing-dependent test (a wall-clock hang guard). Not a mailbox bug, and not ordinary load flakiness.**

Evidence:
1. **Timeline** (`pmset -g log` plus source-file mtimes). The run started 17:50:36 with the lid closed on battery at 3%. The Mac slept at 17:50:57 and 18:01:15, so the script advanced only during brief maintenance wakes (36 minutes in total; the same run takes about 70 s on a settled machine). M13's run ended at 18:25:58, the same second as the wake that ended a 97 s sleep (18:24:21 → 18:25:58): its test process was frozen mid-run.
2. **Mechanism in the code.** The reader ended on `Date() < deadline`, a 60 s *wall-clock* deadline, and wall-clock time keeps running during sleep. The other assertions (`torn`, `backwards`, `newReads`) cannot depend on time, and the algorithm cannot produce torn or backwards reads (the reader only swaps in a slot published after its current one; the `acq_rel` exchanges give the happens-before).
3. **Reproduction.** Freezing the test process (SIGSTOP) for 65 s during a 100M-iteration run made exactly one assertion fail, `r.lastSeq == total` (the reader had seen 22.4M of 100M values), while torn/backwards stayed green: the signature of the original failure.
4. **No failures without a freeze.** 170 valid runs on the unmodified code, 0 failures: stress test alone ×60, whole suite ×30, under ThreadSanitizer ×40 (30 stress + 10 whole suite), with 20 busy processes on 10 cores ×40 (30 stress + 10 whole suite). (An earlier loaded set was INVALID and is not counted: the bundles were still TSan-instrumented from the previous phase and aborted with "Interceptors are not working". Redone correctly.)
5. **Re-run.** The same 18 mutations on a settled machine caught M13 only with its own test (no stress-test failure).

**Fix (test only).** The reader now stops when the writer has finished and it has done one more read. That read starts after the final publish, so a latest-value mailbox must return the final sequence: the verdict uses no clock. Same 65 s freeze and 100M iterations: old design **fails**, new design **passes** (79.5 s, 196M reads). The new test still catches real mailbox bugs: a no-atomics single slot fails `torn == 0`; a reader that never swaps in new data fails `lastSeq == total` in 28 ms (the old design would have spun toward its deadline). Repeats of the new test: 40 plain, 30 under load, 30 under TSan, 0 failures; a 10M-iteration TSan soak is clean.

**The same class of hazard, found by auditing the rest of the suite and fixed:**
- `SimulatedHeadPoseProvider.stop()` was a **real race in production code** (added in Step 2c): it cancelled the timer without waiting for a tick already running, so one more detection could arrive after `stop()` returned, contradicting the protocol's "blocks until released". It now drains the in-flight tick. Regression test `noDetectionIsDeliveredAfterStopReturns`: **6/6 runs fail without the drain, 0/6 with it**.
- `HeadTracker.stopWatchdog()` had the same hole for watchdog snapshots; fixed the same way. Its first regression test was too weak (0/6 failures without the fix, so it proved nothing); it now uses a deliberately slow snapshot handler to keep a tick in flight: **6/6 fail without the drain, 0/6 with it**.
- Fixed sleeps and exact count windows replaced by `waitUntil` (deadline on `SuspendingClock`, which does not advance during sleep) and by an upper bound derived from the measured elapsed awake time; a test that started a real watchdog and asserted an exact snapshot count now disables the watchdog.
Rule recorded in CLAUDE.md: tests never derive a verdict from a wall-clock deadline or fixed sleep.

## App Nap finding (2026-11-04): the app must hold an activity assertion while tracking
While checking the default report path with a simulated run, the loss test began to fail (INCOMPLETE or FAIL, state flapping). The report's own statistics showed why: every run delivered 26.4 fps on average with 125–131 ms frame gaps (≈790 of 900 frames) instead of 30.0 fps and ≈35 ms. Elimination: a bare 30 Hz `DispatchSourceTimer` in a command-line process in the same minute was perfectly regular (33.3 ms, max < 39 ms, at several QoS and leeway settings); the app used only 0–7% of one core and its thread stacks were parked, so nothing was busy or blocked; launching through LaunchServices did not help (foreground launch: 26.4 fps too). Confirmed with the documented `NSAppSleepDisabled=YES` switch on the dev bundle (since removed): **900 frames, 30.0 fps, 33/34/34 ms, PASS**, versus the same minute without it: **789 frames, 26.3 fps, 38/100/130 ms, INCOMPLETE**. So macOS was App-Napping the app because its window was hidden behind others, coalescing its timers.

**Fix.** `HeadTrackingModel` holds `ProcessInfo.beginActivity([.userInitiatedAllowingIdleSystemSleep, .latencyCritical])` from a successful start until stop (API checked in NSProcessInfo.h and by compiling; the "allowing idle system sleep" variant does not keep the Mac awake). With it, simulated runs under the same conditions: 3/3 PASS, 900 / 897 / 900 frames, 30.0 fps. The report now says so when frames stall (statistics note for gaps over 100 ms, loss-test note for gaps over 150 ms); run 2 of those 3 showed a single 134 ms stall and the note fired while the verdict stayed PASS. **Not verified:** whether real camera frame delivery (an AVFoundation callback, not a timer) is affected by App Nap; the assertion is held there too.

## Step 3a findings (2026-11-05): audio-only renderer with a scripted pose, no camera

**SDK facts (macOS 27.2 SDK headers, read on 2026-11-05)**
- `listenerVectorOrientation` default is forward (0,0,-1), up (0,1,0). The header never says which side +X is, so that was MEASURED (below).
- `listenerAngularOrientation.yaw` is documented clockwise-positive; confirmed by reading it back from the node after setting a vector orientation: our yaw +30 (turn LEFT) reads **-30**, our pitch +25 (up) reads +25, our roll +20 (right ear down) reads +20. Hence the conversion uses vectors. (At exactly +-90 degrees yaw the readback degenerates to `(0, 90, 90)`; at 89 degrees it reads -89. Irrelevant for vectors.)
- Getting or setting node properties from a non-realtime thread can require synchronization with the realtime thread, for "some of these properties" that the header does not name (`AVAudioEngine.h`); so the listener setters are treated as control-thread calls. The realtime-safe source-node API is macOS 27+ and `__SWIFT_UNAVAILABLE_MSG("Swift is not supported for use with audio realtime threads")`.
- `connect(_:to:format:)` and `AVAudioPlayerNode.play()` are deprecated from macOS 27 (replacements `connectNode(_:to:format:)` and `playAudio()` throw instead of raising Objective-C exceptions); used behind `#available(macOS 27.0, *)`.
- `HRTFHQ` is in `applicableRenderingAlgorithms` on this Mac (raw values `[0, 1, 2, 6, 3, 7]`). `listenerHeadTrackingEnabled` exists from macOS 15 and is set to false explicitly. Manual rendering must be enabled before touching the mixer/output nodes; the input node is never touched.

**Measurements (offline rendering on this Mac, pink-noise-burst test tone; they describe the engine's output channels, not your headphones)**
- Source at +X / -X / straight ahead: right-minus-left level **+7.7 / -7.7 / -0.3 dB**. (A white-noise probe gave about +-16 dB: the size depends on the signal; the sign is the finding.)
- Head turned (front source): yaw +30 / +60 / +90 degrees (left) → +5.9 / +7.5 / +7.7 dB; yaw -30 / -60 → -6.4 / -7.8 dB. A head turned 90 degrees left renders exactly like a source at +X with the head straight (+7.7 dB both).
- **Rotation invariance.** Listener rotated by R vs. source moved by R^-1, 8 poses (yaw, pitch, roll, combinations): relative RMS difference **0.000000** for all. Rotation applied the wrong way round: 0.48-1.40. Pose ignored: 0.30-1.39. The audio-side flip switches (yaw / pitch / roll flipped) differ from the truth by 1.18 / 0.49 / 0.48, so the same check would catch a sign error.
- Scripted yaw sweep, whole chain offline (script → mailbox → pump → conversion → engine): correlation between each 0.5 s window's expected azimuth and its measured level difference **0.9855**; levels saturate at about +-7.5 dB beyond roughly 50 degrees (monotonic, not linear). With the audio-side yaw flip on, the correlation is below -0.9.
- Live pump timing, one silent run on an idle Mac (battery power, 48 kHz output): 148 ticks, mean period 10.67 ms (nominal 10.67 ms), longest 10.71 ms. The same numbers from the in-app silent self-check: about 200 ticks, mean 10.67 ms, longest 10.7 ms. NOT measured: under CPU load, with heat, with the window hidden for long, over a long run.

## Known limitations of Step 3a (stated, not measured)
- **Not sample-accurate.** The listener is updated once per nominal block by a timer on a non-real-time thread; true per-block interpolation inside a render callback needs a renderer we own (Step 8). Whether `AVAudioEnvironmentNode` smooths orientation changes internally is unknown. τ = 20 ms (the interpolation time constant), the tone level (-26 dBFS RMS in the bursts) and the 30 Hz scripted publish rate are UNTUNED placeholders.
- **Verified against the engine, not against ears.** The conversion is checked against what the node renders (channel levels, exact rotation invariance). Channel 0 = left on the physical headphones, the generic HRTF's quality for any person, externalization and front/back confusion are untested. No personalization.
- **Code paths for macOS 14-26 were compiled but never run.** `connect` / `play` are used in their old forms below macOS 27 (behind `#available`), and this Mac runs 27.2, so only the new forms ran. The package minimum is 14.0.
- **Device change** (headphones plugged in or out while the test runs) only produces a notice and an idle state; not exercised on a real device change. Bluetooth headphones add their own latency, unmeasured here.
- **AirPods-style system head tracking** can not be switched off by this app; the manual test asks the user to turn it off. The app itself sets `isListenerHeadTrackingEnabled = false` (macOS 15+); that assertion is not mutation-checked (the property is already false by default here).
- **ThreadSanitizer cannot see a missing lock around the `Applied` struct copy in the pump** (bulk-memcpy blind spot, same as the mailbox finding); that lock is checked by review only. The scalar timing counters' lock IS covered: with that lock removed and the race window widened by a 1 ms sleep, TSan reports `data race ... ListenerPosePump.timing.getter` (7 reports); on the real code it is clean.
- Volume safety relies on the user's system volume plus the card's slider (default 30%, applied before the engine starts). There is no limiter and no loudness measurement.
- One virtual source only; no distance/room modelling; reverb off; the source is 2 m away with the engine's default inverse-distance attenuation.

### 1. Loss-test flapping (run B)
**What the report shows.** The analysis window (which starts 1 s before the cover cue) began in `decaying`, then `locked, holding, locked, holding, locked, holding, decaying, locked, holding, locked, holding, decaying, static, locked`, with the first hold lasting 0.07 s instead of 0.5 s. So tracking was already lost, and chattering, **before** the cover cue, during the held turn. When the first loss happened the pose was 58.7° away from neutral, while the instruction said "about 25°" (run A: 11.8°). Frames kept flowing normally the whole time (30.0 fps, 33 ms maximum interval, face found in 100% of the statistics-window frames), so this was not a stall or a sleep.

**What the code shows (the mechanism).** The pipeline compared the per-frame quality, the weakest of seven components, with one threshold (0.5). Any score that hovers around 0.5 flips the state on every frame by construction; the synthetic tests now reproduce exactly that chatter with the old single-threshold configuration (`QualityGateConfig.singleThreshold`, 30-60 transitions on hovering quality) and show the new gate does not.

**What is NOT known.** Which component was limiting in run B. The reports did not record it. Likely candidates at a large yaw are face size, Vision confidence and angular speed, but that is a hypothesis; the new "which component limited it" table (per group of phases) will show it in the next real run.

**Change.** `QualityGate`: hysteresis (loss below 0.40, recovery at or above 0.60) and dwell (0.10 s below before loss, 0.20 s above before recovery; a short dip coasts with the pose frozen and nothing fed to the filter; frames that stopped arriving are a loss at once). Tests drive the real pipeline with quality hovering around the threshold (a 3 Hz sine 0.38-0.62, noise inside the band, single-frame and two-frame dips, a lost state that never reaches the recovery threshold) and show 0 chatter, while a real loss still reaches holding / decaying / static on time (hold 0.5 s measured from the declared loss, never a jump) and recovery needs an uninterrupted good stretch. The loss test now also waits for a locked tracker before the cover cue and reports **INVALID** (not FAIL) if tracking was not locked, which is what run B was. The report records the limiting component per phase group. All thresholds are UNTUNED.

### 2. The 16.9° / 18.7° single-frame pose step in LOCKED state
**What the reports show.** A: 16.93°, in `locked`, 2.23 s after the cover cue. The report's "locked before loss" time is 3.23 s counted from the window start (1 s before the cue), so `holding` began about 2.23 s after the cue: the same moment as the step, i.e. the step is on the last locked frame before the loss. B: 18.68°, in `locked`, 6.35 s after the cover cue, which is 0.70 s after the final relock (the relock came 0.65 s after the uncover cue, i.e. at 5.65 s), well past the 0.25 s reacquire blend. Both are far above the 10° threshold and above anything the designed blends produce in these runs (the decay and reacquire blends peak at about 2° per frame or less for the poses involved).

**What is NOT known.** Whether either was a real fast head turn or a Vision outlier. The reports store only the largest step's size and state, not the raw angles around it, so the question cannot be answered from them. One observation, not a conclusion: run A's step sits exactly where tracking was being lost (when the hand covered the lens), the place where a garbage last frame would be expected, but a deliberate quick movement at the cover cue would look the same.

**Change.** The report now stores a numbers-only window (±15 frames) of raw Vision angles, mapped angles, the filtered output pose, state, quality, limiting component and face box around the largest step, plus a shape classification (spike that comes back within 5 frames / movement spread over several frames / abrupt and sustained / face appeared or vanished / output-only, i.e. a blend or filter effect / indeterminate). Thresholds (30% to count as "back", 50% of the 10-frame displacement for "multi-frame", 25% of the output step for "output-only") are untuned and printed. **No outlier rejection or velocity limit was added**, because the data to justify a threshold does not exist and an untested limit risks flattening legitimate fast turns. Decision rule for the next run: a `spike` shape means add a median-of-three or jump-reject stage and justify its threshold from the window; `multiFrameMovement` or `abruptAndSustained` means the step is movement (or a mode switch) and the loss-test threshold, not the tracker, is what needs revisiting; `outputOnly` points at the pipeline. The classifier is tested to never call a 20°-90° turn spread over 2-12 frames a spike.

### 3. Sign-detector noise floor (required movement of 67-70° in run A)
**What the code shows.** The noise figure was **already a robust spread, not a range**: `RobustStats.sigma` = 1.4826 × the median absolute deviation of the instructed axis in the reference window. A value of 14° therefore means that at least half of the 30-45 reference samples differed from the median by roughly 9° or more: the "baseline" window was not still, so the figure measured movement inside the window, not jitter. The values: run A yaw rep 1 14.1° (45 samples of the baseline phase), roll rep 1 13.5°; run B roll rep 1 8.3°, rep 2 4.2°; all others 0.3-3.9°. The raw samples were not stored, so what moved cannot be shown.

**Change (no threshold was loosened).** The requirement is unchanged (max(floor, 5 × robust spread); floors 15° / 10° / 10°; leakage limit 0.6; two agreeing repetitions). The report now prints, for every repetition, baseline statistics of the reference and hold windows per axis (n, median, σ from MAD, range, p10-p90, drift of overlapping sub-windows) so a large figure can be read for what it is, and the reason now says "reference window not steady (spread, drift)" instead of "movement too small" when the reference's own spread sets the requirement. Tests show the figure ignores outliers (4 wild samples out of 40 move σ from about 1° to under 2.5° while the range would have said about 80°) and that an unsteady reference stays unusable. **LIKELY**: a new, clearly separate outcome when at least two repetitions had enough, steady movement and agree on the direction but cross-axis leakage failed. It is shown as "LIKELY (not applied)", never part of `recommendedMapping`, never offered for Apply. On the numbers of these two reports nothing becomes LIKELY (no axis had two repetitions with enough movement and leakage as the only failure), which is the intended conservatism.

### 4. Coaching and a locked start for the loss test
The run panel shows live per-axis bars (deviation from the start pose, target band) with "good / a bit more / too far / other axis moving" during holds and "steady / still moving / not back at the centre" during rests, and asks for about 30° yaw, 20° pitch, 20° roll and 25° for the loss turn, one axis at a time. The cover cue waits until the tracker has been LOCKED for 1.0 s in a row (at most 10 s); otherwise the run ends with the loss test INVALID.

### 5. Why the green-light question was "not asked" in both reports
**What the code shows.** The default value was `not asked` and only a click on one of two buttons replaced it; the buttons sat inside the fifth and last card of the results (below signs, apply, loss and statistics), shown only after the 1.2 s release check. "Copy report" is higher up and copies the report as it is at that moment. Nothing recorded that the question had been displayed, so "not asked" could mean "shown but not answered". It cannot be told from the files whether the question was seen. **Change:** the question is the first thing in the results as soon as they appear (the app has already stopped the camera by then), and it is recorded as **yes / no / not answered**: a real run starts as "not answered", Copy report says so if it is still open, and the files show it. Simulated runs say "not asked (no camera light applies)". Reports written before this change still load (schema 1; the new fields are optional).
