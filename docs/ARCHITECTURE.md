## Head tracking (Step 2)
```
AVCaptureSession (640x480, serial video queue, late frames dropped)
  -> VisionFaceDetector  (VNDetectFaceRectanglesRequest rev 3: yaw/pitch/roll in radians, Vision conventions)
  -> HeadPoseDetection   (timestamps on session sync clock, mirrored flag, rotation angle, error)
  -> HeadTracker         (HeadAngleMapping -> TrackingQualityEstimator -> HeadPosePipeline -> TrackingSnapshot)   [no AVFoundation/Vision here]
       + watchdog timer (monotonic clock): no frame for 250 ms => "lost" tick => hold -> decay -> static
       (planned, Step 3) -> PoseMailbox.publish() -> audio thread PoseMailbox.read() + per-block slerp
  -> HeadTrackingModel   (@MainActor view model) -> HUDView
```
- `HeadPoseProvider` is the seam: the camera implementation is `CameraHeadPoseProvider`; tests use a fake.
- API facts verified against the macOS 27.2 SDK headers on 2026-11-04: Vision `yaw/pitch/roll` exist on `VNFaceObservation` (revision 3 required for pitch and continuous values); header signs: yaw "counterclockwise", pitch "positive = nodding down", roll "counterclockwise"; `AVCaptureConnection.isVideoMirrored` exists on macOS but `automaticallyAdjustsVideoMirroring` does not; `AVCaptureSession.synchronizationClock` (macOS 12.3+) is the timebase of output timestamps.
- Quality gate: `TrackingQualityEstimator` (Core) scores each frame 0...1 as the weakest of: face size, edge cropping, bounding-box jump, scale jump, pose-angle speed, frame rate, Vision confidence. That score, not Vision's confidence, feeds the `QualityGate` (Step 2d): hysteresis (lose below 0.40, recover at or above 0.60) and dwell (0.10 s below before loss, 0.20 s above before recovery; a short dip makes the state machine coast with the pose frozen). Rejected samples never reach the One-Euro filter. Frames that stopped arriving (watchdog) skip the dwell. All four values are UNTUNED. Reason: a single hard threshold chatters when quality hovers around it (the real 08:12 self-test).
- Mirroring: never set; read per frame; yaw and roll signs are flipped by the mapping when a frame is mirrored.
- Latency fields per frame: delivery (received − capture timestamp), vision (detected − received), total (pose ready − capture timestamp).

## Guided self-test (Step 2c) — logic IMPLEMENTED (verified by unit tests); real-camera behavior UNVERIFIED
```
HeadTracker snapshots (+ watchdog ticks)
  -> HeadTrackingModel.receive(snapshot, arrival)         arrival = CLOCK_UPTIME_RAW stamped on the capture queue
  -> SelfTestController   (App: only orchestration + I/O: clock ticks, cue sounds, files, clipboard)
       -> SelfTestSession  (Core, pure: plays SelfTestScript against the clock it is handed; files each frame
                            under the phase it ARRIVED in; emits phase-start events once, in order)
       -> SelfTestAnalyzer (Core, pure)
            SignDetector  : raw Vision angles per instructed move -> per-axis sign or INCONCLUSIVE
            LossAnalyzer  : locked/holding/decaying/static/locked sequence, time in state, largest pose step
            StatsAnalyzer : fps, delivery, Vision, total latency (mean / p95 / max) over the 30 s hold+rest window
       -> SelfTestReport   (Core: numbers + short strings; JSON and markdown; no image data can be expressed)
       -> ReportStore (App) -> docs/test-results/*.json|.md
  -> model.stopAndVerifyRelease() -> CameraReleaseReport (programmatic) -> user answers the green-light question (visual)
```

- **Sign semantics.** The detector works on RAW Vision angles (before `HeadAngleMapping`) as hold-minus-reference differences, so rest offsets cancel. The invert flag it reports is derived by pushing the measured delta through the REAL `HeadAngleMapping` (including its mirror compensation), so it cannot disagree with the mapping. It cannot know which physical direction the person moved; the prompts and the report say so.
- **Thresholds** (all untuned proposals, printed in every report): movement ≥ 15° yaw / 10° pitch / 10° roll and ≥ 5× the reference-window noise; hold spread ≤ 40% of the movement; both repetitions usable and the same sign; other axes ≤ 0.6× the intended one; ≥ 10 reference / 15 hold samples and a face in ≥ 60% of hold frames. Loss test: pose-step threshold = max(10°, 1.25 × the largest step the eased blend could legitimately produce), a held pose < 10° from neutral marks the jump check WEAK.
- **Apply.** Only after an explicit confirmation: sets the invert flags of the DETERMINED axes (inconclusive axes keep their current setting), stores them in `UserDefaults`, and resets the filter, state machine and calibration (they live in mapped space; the user must Recenter). Never applied from a SIMULATED run.
- **Camera release evidence** is what code can prove: `AVCaptureSession.isRunning` read right after `stopRunning()` returned (it "blocks until the session object has completely stopped"), inputs/outputs removed, no sample callbacks after stop. Stop notifications and "session object freed" are INFORMATIONAL (they depend on the run loop and timing; verified on a camera-less session that they arrive only while the run loop spins). The physical green light is a visual check.
- **Simulated user** (`SimulatedUser`, `SimulatedHeadPoseProvider`, `--simulate`): deterministic made-up person for unit tests and for rehearsing the flow without a camera. Fabricated data, labeled SIMULATED everywhere, never usable for decisions about hardware.
- **Step 2d additions** (IMPLEMENTED, unit-tested; real camera UNVERIFIED): `SelfTestSession` has a lock gate (the cover cue waits until the tracker has been LOCKED for 1.0 s, at most 10 s; otherwise the loss test is INVALID); `SelfTestCoach` (Core, pure) turns the live raw angles into per-axis deviations and a good / too small / too far / other-axis-moving verdict for the run panel's bars; `StepEvidenceAnalyzer` stores and classifies the window around the largest pose step; `QualityAnalyzer` attributes low quality to the limiting component per phase group; the sign detector reports baseline statistics and a separate LIKELY outcome that is never applied; the green-light question is recorded as yes / no / not answered. Schema 2; schema 1 reports still decode.

## Conventions (IMPLEMENTED, pinned by tests)
- Right-handed; +X right, +Y up, forward = −Z (matches AVAudioEnvironmentNode).
- Pose: yaw about +Y (positive = turn left), pitch about +X (positive = look up), roll about forward (positive = right ear down). Euler order yaw → pitch → roll; Euler used only at API boundaries.
- Speaker angles use the audio-standard convention instead: azimuth 0 = front, positive = right; elevation positive = up. `Speaker.position()` converts to the frame above.
- `calibrated = neutral⁻¹ · raw`. Pipeline order: One-Euro filter (raw camera space) → calibration → state machine, so decay always returns to calibrated neutral.
- Mirroring/sign handling of the camera is the Tracking module's job (Step 2) and must be verified manually.

## Constraints
- Quaternions internally; Euler only at API boundaries.
- Audio callback: no locks, allocation, I/O or logging.
- Camera frames stay in memory, are never saved, no network code; camera released on stop/exit.
- Core Audio taps need macOS 14.2+; SwiftPM can only declare 14.0, so gate with `#available` at runtime.

## Pose handoff to the audio thread — options (checked 2026-11-04) — DECIDED and implemented: C triple buffer (`CPoseMailbox`)
Requirement: single writer (tracking), single reader (audio callback); no locks, allocation, I/O or logging in the reader. A pose is 4 doubles (32 B) or 4 floats (16 B), too large to rely on a single atomic word, so every lock-free option needs a seqlock or triple buffer built on atomic integer operations.

| Option | Available at macOS 14.0? | Trade-offs |
|---|---|---|
| Swift `Synchronization` (`Atomic`, `Mutex`) | **No.** Verified in the SDK `.swiftinterface`: `Atomic`, `AtomicLazyReference`, `Mutex` are `@available(macOS 15.0)` | Clean Swift API, but would force a macOS 15 minimum, excluding 14.x Macs. Core Audio taps only need 14.2, so this would cost users for no audio reason |
| C target using `<stdatomic.h>` | Yes. Verified: a C file using `atomic_fetch_add_explicit`/`atomic_load_explicit` compiles with clang for `arm64-apple-macos14.0`. Not yet built as a SwiftPM C target | No third-party dependency; explicit memory orders; a triple buffer is ~40 lines of C and is wait-free for reader and writer. Cost: a mixed-language package and careful memory-order review; needs a stress test |
| `swift-atomics` package (Apple) | Not verified here (deployment target and API not checked) | Well-known library, but a new dependency (needs a stated reason); we would still build the triple buffer ourselves |
| Locks (`os_unfair_lock`, even try-lock) | Yes | Violates the no-locks-in-audio-callback rule; priority-inversion risk. Rejected |
| `OSAtomic*` | Present but deprecated in the SDK headers | Rejected |

Decision (approved by Sanjai): C target with a `stdatomic.h` triple buffer, because it works at 14.0 with no dependency and is wait-free for both sides. Implemented as `Sources/CPoseMailbox` + `PoseMailbox` (Core); stress- and TSan-tested (see STATUS). The audio reader will interpolate (slerp) between the previous and latest pose per block. The ARC question that was left open here is DECIDED in "Real-time rule" below.

## Real-time rule (DECIDED 2026-11-05, Step 3a; checked against the macOS 27.2 SDK headers and this toolchain)
**Question.** What may the audio render side touch: a raw C pointer to the `PoseMailbox`, or Swift class access (ARC)? And where does the listener get its pose?

**Facts (each from a header or a measurement, nothing from memory).**
1. `AVAudioEnvironmentNode` exposes the listener only as plain node properties (`listenerVectorOrientation`, `listenerAngularOrientation`, `listenerPosition`); no header text promises real-time safety. `AVAudioEngine.h` (comment on `AVAudioEngineManualRenderingBlock`) says that calling into the engine from a non-realtime thread "(e.g. for setting or getting node properties)" can make the realtime render return `AVAudioEngineManualRenderingStatusCannotDoInCurrentContext`, "because interacting with some of these properties requires synchronization between the realtime and calling threads". It does not say which properties, so the listener setters are treated as control-thread operations (not wait-free) and must not be called from a render callback.
2. `AVAudioSourceNode` (Swift-callable, macOS 10.15+): "The block can be called on realtime or non-realtime threads ... it is the client's responsibility to handle it in a thread-safe manner." The realtime-safe variants (`initWithRealtimeSafeRenderBlock:`, `AVAudioSourceNodeRenderBlockRealtimeSafe`) are macOS 27.0+ only (our minimum is 14.0) and are marked `__SWIFT_UNAVAILABLE_MSG("Swift is not supported for use with audio realtime threads")`.
3. Probe (`swiftc -O -wmo`, Swift 6.4.2, 2026-11-05): reading the mailbox through a `final class` wrapper, through a class stored in another class next to mutable `var` state, and through an escaping closure that captured the class produced NO `swift_retain` / `swift_release` / `swift_beginAccess` / `swift_allocObject` / `malloc` in the hot path (the reader function itself, and the closure body). ARC and allocation appeared only at setup (closure creation, `init`, `deinit`). A closure capturing only a raw-pointer struct had a 3-instruction body. This is what the optimizer did in one build configuration, not a language guarantee: debug builds, public cross-module accessors, `weak` references and a last release on the audio thread (which would `free`) all change it.

**Options.**
| Option | For | Against |
|---|---|---|
| A. Swift class access (`PoseMailbox` as is) on the render side | simplest; optimized build showed no runtime calls | no guarantee; debug/cross-module builds differ; Apple says Swift is not supported on realtime threads |
| B. Raw C pointer + plain-old-data state, C functions only | ARC-free by construction; the C mailbox is already wait-free | a little more plumbing |
| C. Whole render block in C/Objective-C | strictest reading of Apple's Swift note | duplicates quaternion math in C; build complexity |

**Decision.**
- **Step 3a has no custom code on the render thread at all.** The test tone is a pre-rendered 2 s loop (`TestTone`, generated off the audio thread) played by `AVAudioPlayerNode` with `.loops`. The "no locks, allocation, I/O or logging in the audio callback" rule is therefore met by construction: there is no callback of ours.
- **The listener is driven by a pose pump** (`ListenerPosePump`): one tick per nominal render block (512 frames, 10.67 ms at 48 kHz) on a `.strict` timer on its own queue. Each tick reads the `PoseMailbox`, advances the `PoseInterpolator` by the measured time since the previous tick, converts with `ListenerFrame`, and sets `listenerVectorOrientation`. This is ordinary control-thread code (locks and classes are fine there). It is NOT sample-accurate; its jitter is measured and shown (live smoke run: 148 ticks, mean 10.67 ms, max 10.71 ms on an idle Mac), but not under load or thermal stress (Step 5).
- **Rule for any future code that runs on a render thread** (Step 6 system-audio source, Step 8 own renderer): it may touch only raw C pointers, plain structs (no classes, arrays, strings, existentials), and C functions. No Swift class instance access, no closures capturing `self`, no Objective-C messaging, no logging, no allocation, no locks. The mailbox is read through its C API (`SAPoseMailboxRead`). `PoseInterpolator` and `ListenerFrame` are value types with no heap use and are written to be callable from there. One-time observation, 2026-11-05 (NOT a gate; it has to be repeated by hand): disassembling the release `SpatialAudioCore.o` and scanning for `swift_retain|release|bridgeObject*|beginAccess|endAccess|allocObject|swift_once|malloc|free|objc_*` found none in `PoseInterpolator`, `ListenerOrientation`, `ListenerMapping`, `ListenerFrame`, `ListenerGeometry` (100 functions) nor in the `Quaternion` / `Vector3` helpers they call (24 functions); only libm math calls appear. PLANNED: when the first render callback exists, add a release-build disassembly scan for `swift_retain|swift_release|swift_beginAccess|swift_allocObject|malloc|objc_*` on the functions it calls, shown to fail on a deliberately broken variant (CLAUDE.md test-the-test).
- If a render callback must be written in Swift before Step 8, keep its Swift body to one forwarding call into C and verify the disassembly; the fallback is option C.

**Consequence for "pose interpolated per audio block".** With AVAudioEnvironmentNode the finest granularity we can address is one listener update per pump tick, i.e. per nominal block, not per sample and not inside the callback. Whether the node ramps orientation changes internally is unknown (not measured).

## Audio output (Step 3a) — IMPLEMENTED, verified offline; how it sounds is UNVERIFIED
```
ListeningTest script (Core, pure)  --30 Hz-->  PoseMailbox.publish  (producer: ScriptedScenePublisher; stands in for the tracker)
PoseMailbox.read --> PoseInterpolator (slerp toward latest, tau = 20 ms, UNTUNED) --> ListenerMapping (flip switches) --> ListenerFrame
   --> AVAudioEnvironmentNode.listenerVectorOrientation          (consumer: ListenerPosePump, once per block)
AVAudioPlayerNode (mono looping noise-burst tone, position fixed in the room) --> AVAudioEnvironmentNode (outputType .headphones,
   source renderingAlgorithm .HRTFHQ) --> main mixer --> output
```
- **Conversion** (`ListenerFrame.orientation`): `forward = pose.rotate(-Z)`, `up = pose.rotate(+Y)`, handed over as `AVAudio3DVectorOrientation`. Vectors are used on purpose: AVAudio's angular yaw is CLOCKWISE-positive (turn right = +, read back from the node: our left turn of 30° reads yaw = -30), the opposite of this project's yaw (+ = turn left). Pitch (+ = up) and roll (+ = right ear down) agree with ours. Feeding our yaw to `listenerAngularOrientation` would have mirrored left and right.
- **Header facts vs measurements.** The header fixes only the DEFAULT orientation (forward (0,0,-1), up (0,1,0)); it never says which side +X is. Measured by offline rendering: a source at +X is louder in output channel 1 (right) than channel 0 (left), by +7.7 dB with the test tone (and the mirror image for -X; centred source: -0.3 dB). Channel 0 = left / 1 = right is the engine's standard stereo order and is an assumption about the physical headphones until someone listens.
- **Strong check.** For yaw, pitch, roll and combinations, rendering with the listener rotated by R is identical (relative error 0.000000) to rendering with the neutral listener and the source moved by R^-1, and differs by 0.48-1.40 when the rotation is applied the wrong way round. This ties the listener vectors to the engine's own source convention without any assumption about handedness. It cannot tell you whether your headphones are worn the right way round.
- **Listening tests** (`ListeningTest`): A source left / right / ahead with the head still; B head sweep +-60 deg (12 s); C head holds at +-45 deg; D pitch sweep; E roll sweep. Each is a pure function of time. The "expected" text comes from `ListenerGeometry` (identity mapping), i.e. the physical truth, not from the flip switches. Procedure: docs/MANUAL_TEST_STEP3A.md.
- **Flip switches** (`ListenerMapping`): audio-side yaw / pitch / roll negation, for diagnosis during the listening test only. Default identity; never a substitute for fixing the conversion.
- **System head tracking is switched off explicitly** (`isListenerHeadTrackingEnabled = false`, macOS 15+, API in the SDK header) so the system cannot rotate our listener. With AirPods, macOS's own Spatial Audio head tracking is a separate system feature that this app cannot switch off; the manual test says to turn it off.
- **Engine API notes (macOS 27 SDK):** `connect(_:to:format:)` and `AVAudioPlayerNode.play()` are deprecated from macOS 27 in favour of the throwing `connectNode(_:to:format:)` and `playAudio()`; the old forms raise Objective-C exceptions on errors, which Swift cannot catch. The renderer uses the new ones behind `#available(macOS 27.0, *)` and the old ones below. The input node is never touched (no microphone). Offline mode enables manual rendering before touching the mixer/output nodes, as the header requires.

## System audio capture probe (Step 6a) — IMPLEMENTED-UNVERIFIED: built, unit-tested, scanned and TSan-checked; NEVER run against a real tap
Goal: learn, on this Mac, whether a Core Audio process tap gives usable system audio, in what format, and with what permission flow. **Measure only**: no rendering, no camera, nothing muted, the audio is counted and never stored.

**API facts (read from the macOS 27.2 SDK headers, `CoreAudio.framework/Headers`, before any code was written).**

Both are UNVERIFIED until the probe has run: the prompt text, whether the key is really needed, and the behavior when denied are recorded by the manual run (docs/MANUAL_TEST_STEP6A.md). `scripts/make-app.sh` writes the key into the dev bundle (`SA_OMIT_AUDIO_KEY=1` leaves it out for the experiment).

**Design (the smallest that satisfies the Real-time rule).**
- **`CTapProbe` (C11, `<stdatomic.h>`)** holds the only real-time function, `SATapProbeIOProc`, declared with exactly the `AudioDeviceIOProc` signature (nullability aligned with the SDK's `assume_nonnull` so Swift accepts it). It reads the time from the callback's own `inNow->mHostTime`, loops over the input buffers for peak and sum of squares, writes ONE 32-byte `SATapProbeRecord` into a buffer the control thread allocated up front and publishes it with a release store of the committed count. It never touches the audio. No allocation, locks, logging, Objective-C, Swift or calls; a full buffer only increments an atomic `dropped` counter. A format it cannot read (not 32-bit float), a NULL buffer, NaN or infinity are flagged in the record, never guessed. **Frame arithmetic:** the callback divides a byte count by bytes-per-sample x the buffer's channel count, and the channel count comes from the HAL. `SATapProbeCreate` therefore refuses a zero sample size (so the callback can rely on bytes-per-sample >= 1) and the divisor is formed in 64 bits, so it cannot wrap to 0 (with a 32-bit product, 4 x 0x40000000 wraps to 0: a division by zero, undefined behaviour in C, which arm64 turns into 0 and no behavioural test can see). The first version of this step guarded only the sample size and missed the wrap; see the correction in docs/STATUS.md. The control thread reads records field by field after an acquire load of the committed count.
- **`SpatialAudioCore`** (pure, unit-tested): `TapProbeRecord`, `TapProbeAggregator` (frames per callback min / median / max, callback interval, count, per-second peak and RMS, flags, implied frame rate), `CoreAudioStatus` (the status names the header gives, nothing invented), `TapFormat`, `TapProbeReport` (JSON, markdown), and `TapProbeRunner`, the sequence behind a `TapProbeBackend` protocol: lists, own process object, create tap, read UID and format, allocate, create aggregate device, create IO proc, start, wait, lists, stop, destroy IO proc, collect, destroy aggregate device, destroy tap, then poll the lists until both are gone (bounded by a `SuspendingClock`, not a fixed sleep). On ANY failure it unwinds what exists in reverse order and records every call's OSStatus.
- **`SpatialAudioEngine`**: `SystemTapBackend` (the real Core Audio calls, control thread only, `@available(macOS 14.2, *)`), `SimulatedTapBackend` (drives the real C callback from a test thread; reports say SIMULATED), `TapProbeCommand`.
- **`SpatialAudioApp`**: `--tap-probe <seconds>`, `--tap-probe-simulate <seconds>`, `--tap-probe-with-output-device`, `--allow-device-inputs`, `--list-audio-devices`. Probe mode runs inside `App.init` and exits before any window exists; the app module contains no capture code.
- **Composition (UNVERIFIED which one works on this Mac).** Default: a private tap (global stereo mixdown excluding our own process object, `muteBehavior = .unmuted`) in a private aggregate device with the tap list and NO sub-device, the shape of Apple's sample (name and UID only). That avoids pulling an output device's input streams into the aggregate device, which could open a headset microphone or switch a Bluetooth profile. `--tap-probe-with-output-device` adds the default output device as main sub-device and REFUSES if that device has input channels unless `--allow-device-inputs` is given. If this process has no audio process object (the header says the translation then returns `kAudioObjectUnknown`), nothing is excluded and the report says so; the probe plays no audio, so it would not be in the tap either way.

**Real-time and safety checks of the callback (each shown to fail on a deliberately broken variant, see docs/STATUS.md "Step 6a verification record").**
1. *Compile time:* the header marks the callback `CA_REALTIME_API`, which this clang expands to `__attribute__((nonblocking))`; the target is built with `-Werror=function-effects`, so clang rejects any call from the callback to a function it cannot prove non-blocking (`malloc`/`free` inside it is a compile error).
2. *Release disassembly (the scan CLAUDE.md requires):* `scripts/scan-rt-callback.sh` builds release, disassembles `_SATapProbeIOProc` with `otool -tvV` and fails on any call instruction (`bl`, `blr`, ...) or any branch that leaves the function. It reads the code actually generated, not the source (it caught a hidden `memcpy` that a struct copy compiled to). The debug build (-O0) is not scanned.
3. *ThreadSanitizer:* `swift test --sanitize=thread` does not instrument C targets (same finding as for the pose mailbox), so `scripts/tsan-tapprobe.sh` builds `CTapProbe.c` with clang `-fsanitize=thread` and a two-thread stress (a writer calling the real callback while a reader reads published records): clean on the real code, a data race reported on three broken variants (publish before writing, relaxed publish store, relaxed consumer load).
4. *UBSan on the frame arithmetic:* `scripts/ubsan-tapprobe.sh` builds `CTapProbe.c` with clang `-fsanitize=integer-divide-by-zero -fno-sanitize-recover=integer-divide-by-zero` and feeds the callback hostile channel counts (including the one that wraps a 32-bit product to 0). It exits non-zero when the sanitizer fires (recovery is disabled, so the program aborts). It FAILED on the earlier callback (exit 134, `division by zero` at the divide) and passes on the fixed one; it is the only check that can see a wrapped divisor, because arm64 returns 0 for an integer division by zero.

**Open questions this step does NOT settle.**
- **Lifetime of the callback's state.** The header does not say that `AudioDeviceDestroyIOProcID` waits for a callback that is already running, and `AudioHardwareDestroyAggregateDevice` is documented as asynchronous. The real backend therefore never frees the record buffer (the probe process exits right after the run). A renderer (Step 6b) needs a real protocol for this.
- **Verifying teardown from another process.** The tap and the aggregate device are private, so a different process cannot see them, with or without a leak. The evidence is the in-process device and tap lists read before, while running and after teardown (with the post-destroy polling), plus the per-call destroy statuses. `--list-audio-devices` from a fresh process after the exit can only show that nothing visible remains.
- Whether the tap-only aggregate device starts at all, the tap's real format and cadence, whether this process gets an audio process object, what the permission prompt says, and what happens when it is denied. All need the run.
